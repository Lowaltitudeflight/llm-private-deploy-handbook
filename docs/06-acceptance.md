# 06 验收

> **目标**：让客户**签字**，并且这个签字是双方都服气的。
>
> 验收不是"演示一遍"，而是**按事先约定的标准逐项判定**。
> 标准必须在 [P3 方案设计](03-solution-design.md) 阶段就定下来，
> 不能等到验收当天才讨论"什么算合格"。

---

## 6.1 验收的三个层次

| 层次 | 问题 | 判定方式 | 不通过意味着 |
| --- | --- | --- | --- |
| **功能验收** | 该有的能力都有吗？ | 用例逐项执行 | 没做完 |
| **性能验收** | 达到约定的性能指标了吗？ | 按标准压测 | 没做到位 |
| **稳定性验收** | 能长期稳定运行吗？ | 长稳观察 | 有隐患 |

**三个必须都通过才算验收完成。** 常见错误是只做功能验收就签字，
上线两周后出问题，责任说不清。

---

## 6.2 功能验收

### 6.2.1 用例集（可直接作为验收用例表的骨架）

| # | 用例 | 操作 | 预期结果 | 结果 |
| :---: | --- | --- | --- | :---: |
| F01 | 服务健康 | `GET /health` | 200 | ⬜ |
| F02 | 模型列表 | `GET /v1/models` | 含约定模型名 | ⬜ |
| F03 | 基础对话（非流式） | 单轮提问 | 返回合理回答 | ⬜ |
| F04 | 基础对话（流式） | `stream=true` | 逐 token 返回，以 `[DONE]` 结束 | ⬜ |
| F05 | 多轮上下文 | 连续 3 轮追问 | 正确引用前文 | ⬜ |
| F06 | 中文能力 | 中文提问 | 中文回答无乱码 | ⬜ |
| F07 | 长文本输入 | 输入接近 `max_model_len` | 正常处理，不崩 | ⬜ |
| F08 | 超长输入 | 超过 `max_model_len` | 明确报错（400），非静默截断 | ⬜ |
| F09 | 输出长度限制 | `max_tokens=16` | 输出不超过 16 tokens | ⬜ |
| F10 | 停止词 | 传 `stop` 参数 | 在停止词处截断 | ⬜ |
| F11 | 鉴权 - 无 Key | 不带 Authorization | 401 | ⬜ |
| F12 | 鉴权 - 错 Key | 错误 Key | 401 | ⬜ |
| F13 | 异常输入 - 空 messages | `messages: []` | 400，服务不崩 | ⬜ |
| F14 | 异常输入 - 非法 JSON | 畸形 body | 400，服务不崩 | ⬜ |
| F15 | 并发 2 路 | 同时发 2 个请求 | 都正常返回 | ⬜ |
| F16 | 服务重启恢复 | 重启进程 | 自动恢复，参数不变 | ⬜ |
| F17 | 日志与监控 | 查看 Grafana | 能看到 QPS/延迟/显存 | ⬜ |
| F18 | 告警触发 | 人工触发一条告警 | 收到通知 | ⬜ |

> ✅ **F08（超长输入）特别重要**。很多服务对超长输入的处理是
> **静默截断**——用户以为问的是完整文档，实际只截了前 1/4。
> 这种问题在演示时看不出来，在生产上会变成"模型漏读了关键信息"。
> **验收时必须明确：是报错还是截断，必须符合约定，且要在文档里写明。**

### 6.2.2 业务效果验收

这一项**不能用通用 benchmark 代替**。

| 做法 | 说明 |
| --- | --- |
| 准备 **20~50 个客户真实业务问题** | 由客户业务方提供 |
| 每个问题准备**参考答案或评分要点** | 由客户确认 |
| 交付方与客户**分别独立打分**（1~5 分） | 避免单方主观 |
| 计算平均分，与约定阈值比较 | 例如"平均 ≥ 4.0 且无 1 分" |
| 若低于阈值，用**同一批问题**测候选模型/精度 | 定位是选型问题还是部署问题 |

> ⚠️ **必须在 P3 阶段和客户约定"业务效果"是否属于验收项**。
> 如果约定为验收项，那么模型答得不好就是验收不通过，
> 需要用更好的模型或更高精度重来 —— 这会显著影响成本和工期。
> **不要在这件事上含糊过去。**

## 6.3 性能验收标准怎么写

### 6.3.1 一个合格的标准必须包含四要素

```
【前提条件】 + 【负载模型】 + 【指标】 + 【阈值】
```

**❌ 不合格的写法**（客户和交付方各理解一套）：

> "响应要快，能支持多人同时使用。"

**✅ 合格的写法**：

> 在**单副本、8×A100 40G、Qwen2.5-72B-AWQ、max_model_len=8192** 配置下，
> 使用 `vllm bench serve`，输入长度 1024 tokens、输出长度 256 tokens、
> `temperature=0`、充分预热后：
>
> | 指标 | 阈值 |
> | --- | --- |
> | 并发 16 时系统吞吐 | ≥ 500 tokens/s |
> | 并发 16 时 TTFT P95 | ≤ 2000 ms |
> | 并发 16 时 TPOT P95 | ≤ 60 ms |
> | 并发 32 时错误率 | < 0.1% |
> | 连续 1 小时压测显存增长 | < 5% |
>
> **测试机与被测服务分离；客户端 CPU 利用率不超过 60%。**

### 6.3.2 标准模板

| 项 | 内容 |
| --- | --- |
| **硬件配置** | GPU 型号 × 数量、CPU、内存 |
| **软件配置** | 引擎与版本、模型与精度、容器镜像 tag |
| **服务参数** | 完整启动参数（照抄） |
| **负载模型** | 输入长度、输出长度、并发梯度、请求总量 |
| **暖机** | 预热次数 |
| **指标口径** | **TTFT 起点/终点定义**（见 [05 章 5.1](05-benchmark-tuning.md)） |
| **阈值** | 逐指标的合格线 |
| **测量工具** | 工具与版本 |
| **环境要求** | 无其他任务占用、温度正常 |

> ⚠️ **"指标口径"这一行是防扯皮的关键**。
> 写清"TTFT 从客户端发送请求开始计时，到收到第一个 `content` 字段为止，
> 不含客户端渲染时间"，验收时就不会因为口径不同而吵。

## 6.4 稳定性验收

### 6.4.1 长稳测试

| 项 | 建议 |
| --- | --- |
| 时长 | **24h 起步，重要项目 72h** |
| 负载 | 目标并发持续打流（不用峰值，用稳态） |
| 采集 | 每 10s 采一次：延迟、吞吐、显存、GPU 利用率、温度、错误数 |
| 合格线 | 错误率 < 0.1%；**显存无持续增长**；延迟无单调劣化 |

**显存泄漏检测（最容易发现隐患的一项）：**

```bash
# 长稳开始时记录
nvidia-smi --query-gpu=index,memory.used --format=csv > /tmp/mem_start.csv

# 长稳结束时记录
nvidia-smi --query-gpu=index,memory.used --format=csv > /tmp/mem_end.csv

# 对比：增长超过 5% 需要排查
paste /tmp/mem_start.csv /tmp/mem_end.csv
```

> ✅ **判据**：显存应该在负载稳定后**进入平台期**。
> 如果 72 小时内持续缓慢增长（例如每小时涨 200 MB），
> 说明存在**显存泄漏**，服务终究会在某个时刻 OOM。
> **这种问题在 2 小时的短压测里发现不了。**

**延迟劣化检测**：把长稳期间每小时的平均 TTFT 画成曲线。
正常应该是一条水平线；如果逐步上升，说明有资源未释放或缓存膨胀。

### 6.4.2 故障恢复测试

| 场景 | 操作 | 预期 | 恢复时间 |
| --- | --- | --- | --- |
| 进程被 kill | `kill -9 <vllm_pid>` | systemd 自动重启 | ≤ 模型加载时间 + 30s |
| 容器被删 | `docker rm -f` | 自动重建 | 同上 |
| 节点重启 | `reboot` | 开机自启 | 同上 |
| 客户端断连 | 压测中断开 | 服务端不崩，不泄漏 | — |
| 磁盘写满 | 填充日志盘 | 服务降级但不崩，有告警 | — |
| 超长请求轰炸 | 发大量超限请求 | 返回 400，不影响正常请求 | — |

> ⚠️ **恢复时间必须写进 SLA**。大模型重启要重新加载权重，
> 72B 模型可能 3~5 分钟。如果客户以为"重启 30 秒"，
> 上线后第一次故障就会变成信任危机。**提前说清，双方都踏实。**

## 6.5 可复现性验收

**同一配置、同一负载，两次压测结果应该接近。**
如果两次差一倍，说明有未受控的变量。

| 检查项 | 做法 |
| --- | --- |
| 参数快照一致 | 对比两次的启动参数 |
| 输入分布一致 | 用 `--seed` 固定 |
| 环境一致 | 无其他任务、温度正常 |
| 结果差异 | 同一指标两次相差应 < 15%（延迟类 < 25%） |

> ✅ **可复现性本身就是交付质量的一部分**。
> 一个"同样的配置有时快有时慢"的服务，是无法运维的。

---

## 6.6 验收环境的三个"必须一致"

| 必须一致 | 否则 |
| --- | --- |
| **验收环境 = 生产环境** | 在测试机上验收、生产上不达标 → 返工 |
| **验收参数 = 交付参数** | 验收时临时调参、交付时不调 → 扯皮 |
| **验收模型版本 = 交付模型版本** | 验收完又换了模型 → 全部重测 |

> ⚠️ **最常见的坑**：验收在下午做，而机器上**还有别人的任务在跑**，
> 导致 GPU 被争抢、性能不达标。
> **验收前必须确认机器处于干净状态**，并把"无其他任务占用"写进验收条件。

## 6.7 验收流程

```
① 验收准备（T-3天）
   ├─ 交付方提交验收测试方案（含标准）
   ├─ 客户确认标准无异议
   └─ 确认验收时间、参与人、环境干净

② 现场验收（当天）
   ├─ 功能用例逐项执行，现场记录
   ├─ 性能压测（按方案执行，现场看数据）
   ├─ 稳定性数据核对（长稳已提前跑完）
   └─ 异常场景验证

③ 结果判定
   ├─ 全部通过 → ④
   └─ 有未通过项 → 见 6.8

④ 签署
   ├─ 填写验收单（见 templates/acceptance-form.md）
   ├─ 双方签字（建议同时盖章）
   └─ 归档，作为 P7 移交的依据
```

> ✅ **验收当天要"现场出数据"**，不要只拿准备好的报告。
> 客户看到你当场跑、当场看到数字，信任度完全不同。

## 6.8 验收不通过怎么办

**不要慌，也不要含糊。按下面四步走：**

### 第 1 步：确认问题归属

| 现象 | 可能归属 | 验证方式 |
| --- | --- | --- |
| 性能不达标 | 交付方（配置/选型） | 检查参数是否符合方案 |
| 性能不达标但方案里算过 | 需复核估算 | 重算显存/并发 |
| 客户客户端慢 | 客户网络/客户端 | 服务端直接压测对比 |
| 环境有干扰 | 客户环境 | `nvidia-smi` 看是否有其他进程 |
| 业务效果不达预期 | **需回查 P3 约定** | 是否属验收项？ |
| 功能缺失 | 交付方 | 看需求文档 |

### 第 2 步：区分"配置问题"还是"架构问题"

```
是配置问题吗？（参数没调好、量化选激进、并发上限设小了）
├─ 是 → 现场调参重测，当天可能就能过
└─ 否 → 是架构问题
        ├─ 卡数不够 → 需加硬件（走变更流程，工期与费用另议）
        ├─ 模型太大 → 需换模型或加强量化
        └─ 引擎不合适 → 需换引擎（ollama → vLLM）
```

### 第 3 步：出整改计划

必须包含：**问题描述、根因、整改措施、责任人、完成时间、复测方式**。

### 第 4 步：走变更流程

> ⚠️ **如果整改涉及硬件变更或模型替换，必须走正式的变更单/补充协议**，
> 不能口头答应"我们免费给你换"。
> 加卡的采购周期、换模型的重测成本，都要让项目经理和商务知道。

### 一条保护自己的规则

**在验收方案里提前写明"验收不通过的处置流程"**：

> "任一项未通过时，双方应在 3 个工作日内共同确认根因并书面形成整改方案。
> 整改涉及硬件变更、模型替换或超出原方案范围的，按变更流程处理。"

这一句能在出问题时把责任和流程都划清。

## 6.9 常见验收争议与预防

| 争议 | 客户的说法 | 预防措施 |
| --- | --- | --- |
| **并发理解不同** | "我说的是 100 个用户同时用" | P3 阶段明确"并发 = 同时在处理的请求数"，并给出换算经验值 |
| **延迟测法不同** | "我用网页测了要 10 秒" | 口径书面化，且区分服务端延迟与客户端/网络延迟 |
| **提示词不同** | "我随便问了个问题，答得不好" | 用约定的问题集；效果类问题提前约定是否属验收项 |
| **环境不干净** | "就这么测吧" | 验收条件里写明"无其他任务占用"，现场先跑 `nvidia-smi` 确认 |
| **模型版本** | "能不能换个更新的模型" | 更换模型 = 重新验收，写入变更流程 |
| **无限追加需求** | "顺便支持一下文档问答吧" | 需求变更走变更流程，明确工期与费用 |
| **长稳没跑够** | "先上线，有问题再说" | 长稳是验收前置条件，不能后补 |

> ✅ **一条总原则**：**所有可能引起争议的点，都要在 P3 方案的
> "验收标准"一节里白纸黑字写下来，并让客户签字。**
> 验收当天的争执，都是 P3 阶段没写清欠下的债。
