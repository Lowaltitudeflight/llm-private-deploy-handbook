# 05 压测与性能调优

> **目标**：用**可复现的口径**测出服务的真实能力，并据此给出容量结论。
>
> 这一章最重要的是 [5.1 指标口径](#51-指标口径定义先统一口径再谈优化)。
> 交付现场 90% 的"性能争议"，本质是双方对 TTFT 的定义不一样。

---

## 5.1 指标口径定义（先统一口径再谈优化）

### 5.1.1 四个核心指标

| 指标 | 全称 | 定义 | 用户感受 |
| --- | --- | --- | --- |
| **TTFT** | Time To First Token | 请求发出 → **收到第一个内容 token** 的时间 | "按下回车后多久开始出字" |
| **TPOT** | Time Per Output Token | (端到端耗时 − TTFT) / (输出 token 数 − 1) | "出字的速度" |
| **吞吐** | Throughput | 输出 token 总数 / 墙钟时间 | 服务能服务多少人 |
| **P99** | 99th Percentile | 第 99 百分位的延迟 | 最差的那批用户体验 |

### 5.1.2 TTFT 的三个口径陷阱（必读）

`TTFT` 这个词谁都在用，但**测量起点和终点不同，数字能差十倍**。

#### 陷阱 1：TTFT 从哪算起？

| 口径 | 含义 | 什么时候用 |
| --- | --- | --- |
| **从发送请求算** | 含 HTTP 建连 + TLS 握手 + 排队 + 预填充 | ✅ **推荐**，最接近用户真实感受 |
| 从收到 HTTP 200 算 | 不含建连，含排队 + 预填充 | 排除网络噪声，对比引擎性能 |
| 从预填充开始算 | 只含预填充计算 | 纯引擎能力对比，**不是用户体验** |

> ✅ **交付压测用第一种**。但必须在报告里**写明是哪种**，并注明
> "客户端与服务端在同一台机器 / 同机房"，否则网络 RTT 会被算进去。

#### 陷阱 2：算不算排队时间？

**必须算。** 用户按下回车开始等，服务在排队，这个时间用户是真实感受到了的。

> ⚠️ **这就是"并发一高 TTFT 就爆炸"的原因** —— 不是模型变慢了，
> 而是请求在队列里等。**这恰恰是压测最重要的发现之一**，
> 把它排除掉就等于把最关键的结论藏起来了。

#### 陷阱 3：推理模型的"思考段"算不算？

这是**最隐蔽、最容易出错**的一个。

像 DeepSeek-R1、QwQ 这类**推理模型**，会先输出一大段思考内容。
在 OpenAI 兼容的 SSE 流式接口里，这段内容往往走**不同的字段**
（如 `delta.reasoning_content`），而不是 `delta.content`。

```
# 实测现象（通过逐帧解析 SSE 得到）：
帧 1   ~ 帧 128  : delta 里只有 reasoning_content（思考段）
帧 129           : 第一个 delta.content 出现   ← 真正的 TTFT 应该在这里
帧 129 ~ 帧 211  : 正常输出内容
```

- 如果**把第一个任意分片都当作 TTFT** → TTFT 被思考时间严重拉长（虚高）
- 如果**把 reasoning 也算作输出 token** → TPOT 被摊薄（虚低）

> ✅ **正确做法**：
> 1. TTFT 定义为**第一个 `content` 字段**出现的时刻，思考段单独统计为
>    "思考耗时"或一并计入端到端，但要**明确标注**。
> 2. 报告里必须写清目标模型是**推理模型还是普通模型**。
> 3. **做配置对比时不要混用推理模型和普通模型**，指标不可比。

> 📌 **一个真实教训**：用 `deepseek-r1:7b` 做压测目标时，由于思考段的存在，
> 首帧出现在第 1 帧、首个 `content` 出现在第 129 帧（共 211 帧）。
> 如果只取首帧，TTFT 会被严重低估；如果取 `content`，TTFT 又包含了几十秒思考。
> **最终结论是：推理模型不适合作为"TTFT 口径对比"的基准模型。**
> 做压测前先解析一次 SSE 帧结构，确认字段名。

### 5.1.3 吞吐的两种口径

| 口径 | 公式 | 说明 |
| --- | --- | --- |
| **单请求吞吐** | 单请求输出 token 数 / 该请求耗时 | 反映"一个人有多快" |
| **系统吞吐** | **所有**请求输出 token 总数 / 墙钟时间 | 反映"服务能服务多少人" |

> ⚠️ 交付报告里说的"吞吐"**默认指系统吞吐**，因为容量规划看的是它。
> 但一定要写清分母（墙钟时间是从第一个请求发出到最后一个请求结束）。

### 5.1.4 为什么必须看 P99 而不是均值

大模型的延迟分布是**重尾**的。同一配置下：

```
均值 TTFT = 7804 ms
P99  TTFT = 15156 ms   ← 均值看起来还行，但 1% 的用户在等 15 秒
```

只报均值会掩盖真实的最差体验。**交付验收标准应该用 P95/P99。**

### 5.1.5 一个容易忽略的指标：Goodput

**Goodput = 在 SLO 内完成的请求数 / 时间**

例如定义 SLO 为 "TTFT ≤ 2s 且 TPOT ≤ 50ms"，
那么并发 32 时即使"系统吞吐"是 29.3 tok/s，
若大量请求超出 SLO，其 **Goodput 可能为 0**。

> ✅ 容量规划应该看 Goodput，而不是吞吐：
> **"能跑出多少 token" 和 "在可接受的延迟内跑出多少 token" 是两回事。**

## 5.2 压测设计

### 5.2.1 压测参数怎么定

| 参数 | 建议 | 为什么 |
| --- | --- | --- |
| **并发梯度** | 1, 2, 4, 8, 16, 32（**等比数列**） | 等比才能看出饱和拐点在哪一档 |
| **输出长度** | 固定值（如 256 tokens） | 不固定则吞吐不可比 |
| **输入长度** | 固定值，另设一组长输入（如 4K） | 输入长度强烈影响 TTFT |
| **温度** | `temperature=0` | 减少随机性，提高可复现性 |
| **预热** | **至少 2 次**（不计入统计） | 首次请求含编译/CUDA Graph 捕获，会严重拉高数字 |
| **超时** | 给足（如 180s） | 否则高并发下请求被客户端掐断，失败率虚高 |
| **时长** | 每档至少持续到**稳态** | 短时压测容易测到缓存热身阶段的假数据 |
| **重复次数** | 关键档位重复 3 次取中位数 | 单次结果波动可能很大 |

> ⚠️ **预热这一步不能省**。做过的一个对照：不预热时首档 TTFT
> 可能是稳态的 5~10 倍（因为包含 CUDA Graph 捕获、kernel 编译、
> 显存池首次分配）。**不预热就跑的压测数据基本没有意义。**

### 5.2.2 压测提示词设计

**至少覆盖三类：**

| 类型 | 示例 | 测的是 |
| --- | --- | --- |
| **短输入短输出** | "用一句话说明什么是张量并行" | 交互式问答场景 |
| **长输入短输出** | 3000 字的文档 + "总结成三点" | RAG/摘要场景，**最考验预填充** |
| **同前缀多轮** | 固定 system prompt + 不同追问 | 测 prefix caching 收益 |

> ✅ **最好用客户自己的真实业务问题做压测提示词**。
> 用通用提示词测出来的数字，客户会说"跟我业务不一样"。
> 用他的真实数据测，结论就无法反驳。

### 5.2.3 客户端不能成为瓶颈

这是**最容易被忽略、又最容易导致错误结论**的一点：

| 客户端瓶颈 | 现象 | 对策 |
| --- | --- | --- |
| Python 单线程 GIL | 并发 16 时客户端 CPU 先打满 | 用多进程 / 异步 / 独立压测机 |
| 压测机与服务同机 | 争抢 CPU 和网络 | **压测机要与被测服务分离** |
| SSE 解析开销 | 客户端解析比服务端生成还慢 | 简化解析逻辑，或直接用官方压测工具 |
| 连接池太小 | 并发上不去 | 放大连接池 |

> ✅ **判断方法**：压测时**同时监控客户端和被服务端的 CPU**。
> 如果客户端 CPU 先到 100%，说明瓶颈在客户端，这组数据无效。

## 5.3 压测工具

| 工具 | 特点 | 适用 |
| --- | --- | --- |
| `vllm bench serve` | vLLM 官方，指标口径规范 | **首选**（vLLM 部署） |
| `evalscope`（原 llmperf） | 阿里出品，支持多后端 | 通用 |
| Locust | 灵活可编程，可写复杂场景 | 业务场景模拟 |
| 自研脚本 | 完全可控，可定制指标 | 需要特定口径时 |
| `wrk` / `vegeta` | HTTP 层压测 | 测网关/限流，不测模型 |

**vLLM 官方压测：**

```bash
# 需要先起好服务
vllm bench serve \
  --backend openai-chat \
  --base-url http://localhost:8000 \
  --model qwen2.5-72b \
  --tokenizer /models/Qwen2.5-72B-Instruct \
  --endpoint /v1/chat/completions \
  --dataset-name random \
  --random-input-len 1024 \
  --random-output-len 256 \
  --num-prompts 200 \
  --max-concurrency 16 \
  --request-rate inf \
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,90,99 \
  --seed 42
```

> ✅ `--seed 42` 固定随机，保证不同配置间的输入分布一致，结果可对比。

## 5.4 调优矩阵

按"收益 / 代价"排序，从最划算的开始调。

### 第一梯队：收益最大、代价最小

| 调优项 | 做法 | 收益 | 代价 |
| --- | --- | --- | --- |
| **开启前缀缓存** | `--enable-prefix-caching` | 多轮/固定 system prompt 场景 **TTFT 降数倍** | 显存略增 |
| **开启分块预填充** | `--enable-chunked-prefill` | **P99 显著改善**，长请求不再阻塞短请求 | 略微增加调度开销 |
| **关闭请求日志** | `--disable-log-requests` | 消除日志 I/O 抖动 | 失去逐请求日志（有其他监控可补） |
| **预热** | 压测前发几次请求 | 数据真实 | — |

### 第二梯队：需要权衡

| 调优项 | 调大 | 调小 |
| --- | --- | --- |
| `--max-num-seqs` | 吞吐↑，但 TTFT↑、显存压力↑ | 延迟↓，但吞吐↓ |
| `--max-num-batched-tokens` | 吞吐↑（GPU 更满） | TTFT↓（短请求更快被处理） |
| `--max-model-len` | 支持长文本 | **KV 池变大 → 并发能力↑** |
| `gpu-memory-utilization` | KV 池大 → 并发↑ | 与别的业务共卡时更安全 |

### 第三梯队：结构性调整

| 方向 | 做法 | 适用 |
| --- | --- | --- |
| **KV 量化** | `--kv-cache-dtype fp8` | KV 显存减半，**并发能力近乎翻倍** |
| **权重量化** | AWQ / INT8 | 显存大降，代价是精度 |
| **加副本** | DP，多进程/多容器 | 单副本已饱和时**唯一有效的扩吞吐手段** |
| **改并行策略** | TP→DP，或 TP=4×DP=2 | 拓扑不佳时（如 4+4 分组） |
| **换引擎** | ollama → vLLM | 需要真正的生产级并发 |

### 千万不要做的"优化"

| ❌ 做法 | 为什么不行 |
| --- | --- |
| 把 `gpu-memory-utilization` 设到 0.99 | 没有激活空间，必然 OOM |
| 生产开 `--enforce-eager` | 关掉 CUDA Graph，吞吐明显下降 |
| 无脑加大 `--max-num-seqs` | 超过 KV 池容量后就是排队，TTFT 反而爆炸 |
| 不看 P99 只看均值 | 会漏掉最严重的尾延迟问题 |
| 不预热就跑压测 | 数据不可用 |
| 用推理模型做 TTFT 基准 | 口径不可比（见 5.1.2） |

## 5.5 怎么从曲线得出结论

压测出数据只是第一步，**能读出结论才是交付能力**。

### 5.5.1 三类曲线的标准形态

```
① 吞吐 vs 并发
   吞吐
    │            ┌──────────────  平台期（饱和）
    │        ┌───┘
    │    ┌───┘                    ┐
    │ ┌──┘                        │ 有些配置后期会反降
    │┌┘                           ┘（排队开销 / 显存压力）
    └────────────────────────────▶ 并发
       上升段     拐点     平台段

② TTFT vs 并发
   TTFT
    │                              ╱  陡增段
    │                          ╱
    │                     ╱         ← 拐点往往与①的饱和点重合
    │              ╱
    │    ╱
    └────────────────────────────▶ 并发

③ TPOT vs 并发
   TPOT
    │  ─────────────────────────  恒定 → 瓶颈在调度/排队，不在算力
    │  ─────────────────────────
    │                            ╱ 上升 → 计算开始成为瓶颈
    └────────────────────────────▶ 并发
```

### 5.5.2 判读口诀

| 现象 | 含义 | 该怎么调 |
| --- | --- | --- |
| 吞吐线性上升，未到平台 | 资源还没用满 | 可以继续加并发 |
| 吞吐平台 + TTFT 陡增 | **排队饱和**（最典型） | 加副本 / 提 KV 池 |
| 吞吐反降 | 排队开销或显存压力过大 | 停机排查，不要再加压 |
| TTFT 平 + TPOT 涨 | **计算受限** | 提算力（更好的卡/更小模型/更强量化） |
| TTFT 涨 + TPOT 平 | **调度受限** | 典型是调度器/并发上限卡住（见 5.6 案例） |
| P99 远大于 P50（>5 倍） | 存在长尾阻塞 | 开 chunked prefill；检查是否有超长请求 |
| 失败率 > 0 | 先解决错误再谈性能 | 看日志定位 |

> ✅ **"TTFT 涨 + TPOT 平" 这个组合最能说明问题**：
> 每个 token 的生成速度没变（说明算力没变紧），
> 但等待时间在涨（说明请求在排队）。
> **结论必然是"瓶颈在调度层，加算力无用，要加副本或优化调度"。**
> 这是一个非常有力、也非常容易被误读的结论 —— 很多人看到延迟涨就想着换更好的卡，
> 其实是白花钱。

## 5.6 【实测案例】单卡 8GB 消费级 GPU 的完整压测

> 这一节的目的是**演示"怎么从压测数据得出结论"**，
> 同时演示怎么**诚实地标注数据的适用边界**。

### 5.6.1 运行环境（可复现口径）

| 项 | 值 |
| --- | --- |
| 引擎 / 模型 | ollama / `qwen2.5:7b` |
| 量化 | Q4_K_M |
| GPU | NVIDIA GeForce RTX 4060 Laptop，**8.0 GiB** |
| 系统 | Windows 11（10.0.22631） |
| 压测参数 | 并发 1/2/4/8/16/32；每请求 256 tokens；预热 2 次；`temperature=0`；流式；超时 180 s |
| 提示词 | 固定单一提示词 |
| 总量 | 63 个请求（1+2+4+8+16+32）；总耗时 222.9 s；305 个显存采样点 |

### 5.6.2 主结果

| 并发 | 吞吐 (tok/s) | 加速比 | TTFT 均值 (ms) | TTFT P99 (ms) | TPOT (ms) | 端到端 P99 (ms) | 失败率 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 26.9 | 1.00× | 168.81 | 168.81 | 21.64 | 2159.52 | 0% |
| 2 | 27.3 | 1.02× | 1335.32 | 2436.17 | 23.93 | 4607.57 | 0% |
| 4 | 30.4 | 1.13× | 3636.49 | 6869.47 | 23.44 | 8871.39 | 0% |
| **8** | **30.8** | **1.14×** | 7804.78 | 15156.92 | 22.96 | 17178.87 | 0% |
| 16 | 30.0 | 1.11× | 15979.12 | 30537.79 | 21.56 | 32414.35 | 0% |
| 32 | 29.3 | 1.09× | 30839.10 | 60821.14 | 21.69 | 62798.84 | 0% |

显存：峰值 **5.6 GiB / 8.0 GiB（70.3%）**；平均 GPU 利用率 71.9%。
**全部 63 个请求零失败。**

### 5.6.3 三条结论（怎么读这张表）

**结论 1：并发 2 就已经饱和**

并发 1→2 吞吐只涨了 **1.5%**（26.9 → 27.3），之后最高加速比只有 **1.14×**。
说明该引擎在单卡消费级 GPU 上的**并发扩展能力极弱**。

→ 对应 [5.5.2 判读口诀](#552-判读口诀) 的"吞吐平台"。

**结论 2：饱和后继续加压，只推高延迟、不涨吞吐**

并发 32 时：
- 吞吐不升反降（30.8 → 29.3 tok/s）
- TTFT 从 168.81 ms 涨到 **30839.10 ms** —— **恶化 182 倍**

→ 这是"**盲目加并发并不能提升服务容量**"最直接的证据。
容量规划必须建立在**饱和点**上，而不是"并发数越大越好"。

**结论 3：TPOT 几乎不随并发变化（21.6 ~ 23.9 ms）**

单 token 生成速度基本恒定，而等待时间爆炸性增长。

→ 按 [5.5.2 判读口诀](#552-判读口诀)，这是典型的
**"TTFT 涨 + TPOT 平" = 调度受限**。
**说明瓶颈不在算力（换更好的卡没用），而在请求调度/排队。**

**→ 可执行的调优方向：换用调度更好的引擎（如 vLLM 的 PagedAttention 调度）、
或增加副本，而不是升级 GPU。**

### 5.6.4 ⚠️ 这组数据的适用边界（必须标注）

| 能说明 | 不能说明 |
| --- | --- |
| ✅ 该引擎在该硬件上的并发扩展特性 | ❌ 任何数据中心级 GPU 的性能 |
| ✅ "饱和点 + 延迟恶化"这一**现象与判读方法** | ❌ vLLM / TensorRT-LLM 的表现 |
| ✅ 消费级单卡在并发场景下的能力上限 | ❌ 7B 以上模型的性能 |
| ✅ 压测链路（指标口径、统计、报告）的正确性 | ❌ 生产环境的绝对数值 |

> ⚠️ **引用红线**：
> - 这是 **ollama**，不是 vLLM；ollama 的调度是为单用户设计的。
> - 这是**笔记本 GPU**（8 GB、功耗受限），与数据中心卡完全不同量级。
> - 这是 **7B Q4 量化**模型，不是 72B FP16。
>
> **把这组数字写成"我们在 8 卡 A100 上实测 vLLM 性能 XXX"，就是造假。**
>
> 正确的引用方式是描述**方法与结论**：
> "通过并发梯度压测定位到服务的吞吐饱和点，并区分出调度瓶颈与算力瓶颈，
> 给出容量配置建议。"

## 5.7 压测前 Checklist

开始压测前逐项确认，能避免大部分"测出来数据没法用"的情况。

| # | 检查项 | 为什么 |
| :---: | --- | --- |
| 1 | 指标口径已与客户书面统一（TTFT 起点/终点） | 避免验收扯皮 |
| 2 | 目标模型不是推理模型，或已确认 SSE 字段结构 | 避免口径错误（5.1.2） |
| 3 | 已预热（≥2 次） | 避免测到冷启动 |
| 4 | `temperature=0`、`seed` 固定 | 可复现 |
| 5 | 输入/输出长度固定 | 可比 |
| 6 | 压测机与被测服务分离 | 避免客户端瓶颈 |
| 7 | 客户端 CPU/内存有余量 | 同上 |
| 8 | 已关闭服务端逐请求日志 | 避免 I/O 抖动 |
| 9 | 显存、GPU 利用率、温度同时在采集 | 事后能解释异常 |
| 10 | 环境与勘察/方案一致（没人在跑别的任务） | 可比 |
| 11 | 记录了完整的运行参数快照 | 可复现 |
| 12 | 报告里标注了**数据适用边界** | 避免被误引用 |
