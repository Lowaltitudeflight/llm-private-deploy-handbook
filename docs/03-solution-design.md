# 03 部署方案设计

> **目标**：把"客户想要一个能用的对话服务"翻译成一份**参数级确定**的方案：
> 什么模型、什么精度、几张卡、怎么并行、服务怎么暴露、能扛多少并发。
>
> 这一章最核心的是 [3.3 显存估算](#33-显存估算怎么算才不翻车) —— 
> 交付翻车的第一大原因就是估算时只算了权重。

---

## 3.1 从需求到方案的三步转化

```
业务需求                技术指标                    方案参数
─────────────────────────────────────────────────────────────
"要能读懂我们 50 页   →  上下文 ≥ 32K tokens    →  --max-model-len 32768
 的产品手册"                                       模型需支持 32K

"客服部门 30 人同时   →  并发 ≥ 30，              →  --max-num-seqs 32
 用，回答要快"           TTFT P95 ≤ 2s              KV Cache 预算 ≥ 30×2K ctx
                                                     可能需要 2 副本

"回答必须准确，       →  用 FP16 或 AWQ，          →  --quantization awq
 不能掉点太多"           需提供精度对比测试          （而非 GPTQ-4bit 激进量化）
```

> ✅ **转化时一定要把"业务词"变成"数字"**，并在方案里写清换算过程。
> 客户不会认可"应该够用"，只会认可"按 30 并发 × 2K 上下文算，KV Cache 需要 12 GB，
> 当前余量 19 GB，满足要求"。

## 3.2 模型选型

### 3.2.1 选型的五个维度

| 维度 | 要问的问题 | 影响 |
| --- | --- | --- |
| **规模** | 7B / 14B / 32B / 72B？ | 直接决定显存与卡数 |
| **中文能力** | 中文场景表现如何？ | 有些海外模型中文明显弱 |
| **上下文长度** | 需要 4K / 32K / 128K？ | 直接决定 KV Cache 显存 |
| **架构** | Dense 还是 MoE？ | MoE 需要 EP，显存分布不均 |
| **许可协议** | 商用是否允许？ | **法务风险，必须确认** |
| **生态支持** | 目标引擎是否已支持？ | 太新的模型可能要等适配 |

### 3.2.2 参考对照（常见开源模型）

| 模型 | 参数 | 上下文 | 许可 | 备注 |
| --- | --- | --- | --- | --- |
| Qwen2.5-7B-Instruct | 7.6B | 32K | Apache-2.0 | 中文强，单卡可跑，交付友好 |
| Qwen2.5-14B/32B | 14.7B/32.5B | 32K | Apache-2.0 | 32B 是"效果/成本"平衡点 |
| Qwen2.5-72B | 72.7B | 32K | Qwen 许可 | 需多卡，效果接近闭源 |
| Llama-3.1-8B/70B | 8B/70B | 128K | Llama 社区许可 | 长上下文强，中文一般 |
| GLM-4-9B | 9B | 128K | 自定义 | 中文好，长上下文 |
| DeepSeek-V3 / R1 | 671B(MoE) | 128K | 自定义 | 需大量显存，MoE 要 EP |
| InternLM2.5-20B | 20B | 1M | Apache-2.0 | 超长上下文场景 |

> ⚠️ **许可协议是交付的红线**。客户如果用于商业产品，选一个"仅限研究"的模型
> 会带来法务风险。选型阶段就要把许可协议原文摘出来给客户确认。

> ⚠️ **"效果差不多"要客户自己判断**。方案里应附一组**业务问题的对比测试**
> （用客户自己的 20~50 个真实问题分别问候选模型），而不是只给 benchmark 分数。

## 3.3 显存估算（怎么算才不翻车）

显存由三部分组成：

```
总显存需求 = 权重显存 + KV Cache 显存 + 激活/框架开销
```

**三项都要算，且最后乘 1.2~1.3 的安全系数。**

### 3.3.1 权重显存

```
权重显存 = 参数量 × 每参数字节数
```

| 精度 | 每参数字节 | 说明 |
| --- | ---: | --- |
| FP32 | 4.0 | 训练用，推理不用 |
| **FP16 / BF16** | **2.0** | 推理默认，精度最好 |
| FP8 | 1.0 | 需 H100/L40S 等支持 |
| INT8 (W8A8) | 1.0 + 少量 scale | 精度损失小 |
| **INT4 (AWQ/GPTQ)** | **≈0.55** | 含 scale/zero point，实际约 0.5~0.6 |
| GGUF Q4_K_M | ≈0.55 | llama.cpp 生态 |

**常用结果速查（GB）：**

| 模型 | FP16 | INT8 | INT4 |
| --- | ---: | ---: | ---: |
| 7B（7.6B） | 15.2 | 7.6 | 4.2 |
| 14B（14.7B） | 29.4 | 14.7 | 8.1 |
| 32B（32.5B） | 65.0 | 32.5 | 17.9 |
| 72B（72.7B） | **145.4** | 72.7 | 40.0 |
| 70B（Llama-3.1） | 140.0 | 70.0 | 38.5 |

> 📌 **算的时候用真实参数量**，别用"7B/72B"这种约数。
> 以模型目录下 `config.json` 里的字段为准，或用 `safetensors` 文件总大小直接量。

### 3.3.2 KV Cache 显存（最容易被漏掉的一项）

```
单 token KV 字节 = 2 × 层数 × KV 头数 × head_dim × 字节数
```

（`2` = Key 和 Value 各一份；字节数 = 精度，FP16 为 2，FP8 为 1）

**各模型单 token KV 占用（FP16）：**

| 模型 | 层数 | KV 头数 | head_dim | 单 token | 8K 上下文 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Qwen2.5-7B | 28 | 4 | 128 | 56 KiB | 448 MiB |
| Qwen2.5-14B | 48 | 8 | 128 | 192 KiB | 1.5 GiB |
| Qwen2.5-32B | 64 | 8 | 128 | 256 KiB | 2.0 GiB |
| Qwen2.5-72B | 80 | 8 | 128 | **320 KiB** | 2.5 GiB |
| Llama-3.1-8B | 32 | 8 | 128 | 128 KiB | 1.0 GiB |
| Llama-3.1-70B | 80 | 8 | 128 | 320 KiB | 2.5 GiB |

> **GQA（分组查询注意力）的威力**：Qwen2.5-72B 有 64 个注意力头，
> 但只有 **8 个 KV 头**（8:1 分组）。如果按 64 个 KV 头算，
> 单 token 就是 2.5 MiB、是实际值的 8 倍。
> **算之前一定先看 `config.json` 的 `num_key_value_heads`。**

**总 KV 需求：**

```
KV 总需求 = 单 token 字节 × 平均上下文长度 × 并发数
```

> ⚠️ 这里的"并发数"是**同时在处理的序列数**，不是"在线用户数"。
> 用户在看回答时不产生新 token，不占算力但**占着 KV Cache**（除非服务做了超时释放）。
> 经验上按 **在线用户数的 20%~50%** 估算同时活跃数。

### 3.3.3 激活与框架开销

这部分难以精确计算，给经验值：

| 项 | 经验值 |
| --- | --- |
| CUDA Context / 引擎基础开销 | 0.5 ~ 1 GB / 卡 |
| 激活值（随 batch × seq 增长） | 1 ~ 4 GB / 卡 |
| 通信缓冲区（TP/PP） | 0.5 ~ 2 GB / 卡 |
| 显存碎片预留 | 约占可用显存 5%~10% |

**简单记法：每卡预留 2~4 GB 给激活与框架；长上下文场景取上限。**

### 3.3.4 三个完整算例

#### 算例 1：Qwen2.5-7B FP16，单卡 A100 40G，8K 上下文

| 项 | 计算 | 结果 |
| --- | --- | ---: |
| 权重 | 7.6B × 2 | 15.2 GB |
| 可用显存 | 40 GB × 0.90（`gpu_memory_utilization`） | 36.0 GB |
| 减激活/框架 | 取 1.5 GB | 34.5 GB |
| **KV Cache 池** | 36.0 − 15.2 − 1.5 | **19.3 GB** |
| 单序列 8K 占用 | 56 KiB × 8192 | 448 MiB |
| **可支持并发** | 19.3 × 1024 / 448 | **≈ 44 路** |

✅ 结论：单卡 A100 40G 可以同时服务约 44 路 8K 上下文请求，
设置 `--max-num-seqs 32`（留余量）即可。

#### 算例 2：Qwen2.5-72B FP16，8 × A100 80G，32K 上下文

| 项 | 计算 | 结果 |
| --- | --- | ---: |
| 权重 | 72.7B × 2 | 145.4 GB |
| 可用显存 | 640 GB × 0.90 | 576 GB |
| 减激活/框架/通信 | 4 GB × 8 | 32 GB |
| **KV Cache 池** | 576 − 145.4 − 32 | **398.6 GB** |
| 单序列 32K 占用 | 320 KiB × 32768 | 10 GiB |
| **可支持并发** | 398.6 / 10 | **≈ 39 路** |

✅ 结论：8×A100 80G 跑 72B FP16 全 32K 上下文，只能撑约 39 路。
若客户要 100 并发，必须**降上下文**或**改用 AWQ 量化**（见算例 3）。

> ⚠️ **这个算例说明了一件事**：72B FP16 + 32K 上下文是很奢侈的组合。
> 很多方案报的是"能跑起来"，但并发能力被 KV Cache 死死限制住。
> **方案里必须把并发能力算出来写进去**，否则验收时的性能目标就是拍脑袋。

#### 算例 3：Qwen2.5-72B AWQ INT4，8 × A100 40G，8K 上下文

| 项 | 计算 | 结果 |
| --- | --- | ---: |
| 权重 | 72.7B × 0.55 | 40.0 GB |
| 可用显存 | 320 GB × 0.90 | 288 GB |
| 减激活/框架 | 3 GB × 8 | 24 GB |
| **KV Cache 池** | 288 − 40 − 24 | **224 GB** |
| 单序列 8K 占用 | 320 KiB × 8192 | 2.5 GiB |
| **可支持并发** | 224 / 2.5 | **≈ 89 路** |

✅ 结论：量化把并发能力从"约 39 路（32K）"提到"约 89 路（8K）"，
代价是权重从 145 GB 降到 40 GB、且需接受量化精度损失。
**这正是"精度 vs 容量"决策的量化依据。**

### 3.3.5 估算完成后的反向校验

方案定稿后，**实际跑起来用命令核对**：

```bash
# 看 vLLM 的显存分配日志（启动时会打印）
# "GPU KV cache size: XXX tokens" 和 "Maximum concurrency for XXX tokens per request: Y.Yx"

# 实时观察
nvidia-smi --query-gpu=index,memory.used,memory.total,utilization.gpu \
           --format=csv -l 5

# 通过 Prometheus 看 KV Cache 使用率
curl -s localhost:8000/metrics | grep gpu_cache_usage_perc
```

> ✅ **一条重要的判据**：正常负载下 `gpu_cache_usage_perc` 应在
> **20% ~ 70%** 之间。
> - 长期 > 90% → 并发压力接近上限，请求开始排队，TTFT 会陡增
> - 长期 < 10% → 显存浪费，可以调大 `--max-num-seqs` 或降低卡数

## 3.4 量化方案

| 方案 | 显存降至 | 精度损失 | 速度 | 适用场景 |
| --- | ---: | --- | --- | --- |
| **FP16 / BF16** | 基准 | 无 | 基准 | 精度要求高、显存充足 |
| **FP8** | 1/2 | 极小 | 更快（H100/L40S） | 新卡，精度与速度兼顾 |
| **INT8 (W8A8)** | 1/2 | 小 | 相近或略快 | 通用 |
| **AWQ (W4A16)** | ~1/3.6 | 小~中 | 略慢于 FP16（反量化开销） | **最常用**，激活保持 FP16 |
| **GPTQ (W4A16)** | ~1/3.6 | 小~中 | 略慢 | 与 AWQ 类似，生态更老 |
| **GGUF Q4_K_M** | ~1/3.6 | 中 | 单机友好 | llama.cpp / ollama |

**选量化方案的三条经验：**

1. **优先 AWQ 而不是 GPTQ**。AWQ 对激活值的保护更好，同 bit 下通常掉点更少，
   且 vLLM 支持成熟。

2. **INT8 是"性价比最高"的折中**。显存减半、掉点很小，
   显存刚好卡在临界点时优先考虑 INT8 而不是 INT4。

3. **量化后必须做精度对比测试**，且要留证据：
   ```bash
   # 用同一组业务问题分别问 FP16 与量化版本，人工或 LLM 打分对比
   # 建议把 20~50 个真实业务问题 + 两组回答存档，作为方案附件
   ```

> ⚠️ **不要在没验证的情况下用"激进量化"**（如 2bit/3bit）。
> 交付场景下，模型答得不对比跑得慢严重得多。

## 3.5 并行策略（TP / PP / DP / EP）

### 3.5.1 四种并行的本质区别

| 策略 | 切什么 | 通信量 | 显存收益 | 适用 |
| --- | --- | --- | --- | --- |
| **TP**（张量并行） | 切**每一层**的权重矩阵 | **大**（每层 2 次 AllReduce） | 权重 ÷ TP | 单机内，需 NVLink/高带宽 |
| **PP**（流水线并行） | 按**层**切成若干段 | 小（只在段边界传激活） | 权重 ÷ PP | 跨机，有 bubble |
| **DP**（数据并行） | **复制**整个模型 | 仅请求分发 | 无（反而 × DP） | 提升总吞吐 |
| **EP**（专家并行） | 切 **MoE 专家** | 中（All2All） | 权重 ÷ EP | MoE 模型专用 |

### 3.5.2 决策流程

```
模型能在单卡装下吗？
├─ 能（含 KV Cache + 激活）
│   └─▶ TP=1，最简、无通信开销
│       追求吞吐就加 DP（多副本）
│
└─ 不能
    ├─ 单机内的卡够吗？
    │   ├─ 够 → 首选 TP = 单机卡数
    │   │   ⚠️ 前提：这些卡之间有 NVLink 或全速 PCIe
    │   │   若拓扑是 4+4 两组 → 用 TP=4 × DP=2 而不是 TP=8
    │   │
    │   └─ 不够 → 跨机
    │       ├─ 网络 ≥ 100 Gb IB/RoCE → TP=8（机内）× PP=机器数
    │       ├─ 网络一般（25 Gb）→ 只用 PP，不用跨机 TP
    │       └─ 或改用 TP=4 × PP=机器数
    │
    └─ 是 MoE 模型吗？
        └─ 是 → 加 EP，注意专家负载均衡
```

### 3.5.3 关键经验值

| 规则 | 说明 |
| --- | --- |
| **TP ≤ 8** | TP 的通信量与卡数相关，超过 8 卡后通信收益递减甚至变负 |
| **TP 尽量在单机内** | 跨机 TP 对网络要求极高，25 Gb 网下几乎不可用 |
| **PP 段数 = 机器数** | 跨机时优先用 PP，通信量小得多 |
| **PP 需要微批** | 否则流水线气泡会吃掉 30%+ 的算力（vLLM 自动处理） |
| **TP 数不能大于注意力头数** | 例如 8 个 KV 头的模型，TP 超过 8 无法整除 |
| **DP 是提升吞吐的正道** | 单副本饱和后，加副本比加大 TP 更有效 |

> ⚠️ **TP 的隐性成本**：TP 每层都要做 AllReduce。batch 小的时候，
> 通信延迟无法被计算掩盖，**延迟反而比单卡更差**。
> 所以 TP 适合"吞吐场景"，不适合"极致低延迟的少量请求场景"。
> 低延迟小流量场景，宁可多开几个 DP 副本。

## 3.6 推理引擎选型

| 引擎 | 核心优势 | 劣势 | 适合场景 |
| --- | --- | --- | --- |
| **vLLM** | PagedAttention 高吞吐、社区最活跃、OpenAI 兼容、量化/并行支持全 | 大版本间 API 有变动 | **生产首选**，通用 |
| **SGLang** | RadixAttention 前缀缓存极强、结构化输出、部分场景吞吐更高 | 生态小于 vLLM | 多轮对话、共享前缀、结构化输出 |
| **TGI** | Rust 实现稳定、HF 官方、可观测性好 | 吞吐略低于 vLLM | 稳定优先、HF 生态 |
| **TensorRT-LLM** | 极致性能（尤其大 batch） | 编译复杂、模型支持滞后、调试困难 | 模型固定、长期运行、追求极限 |
| **lmdeploy** | 国产（上海 AI Lab）、TurboMind 引擎、InternLM 优化好 | 模型覆盖面窄 | 信创、InternLM 系 |
| **ollama** | 部署极简、量化方便（GGUF）、本地开发友好 | **并发能力弱**、生产特性少 | 开发验证、单用户、边缘设备 |
| **llama.cpp** | CPU/GPU 混合、极致低资源 | 吞吐低 | 无 GPU、嵌入式 |

### 选型决策建议

```
需要生产级高并发？
├─ 是 → 精度要求极致？（固定模型、追求极限性能）
│        ├─ 是 → TensorRT-LLM
│        └─ 否 → vLLM（默认）/ SGLang（前缀复用多）
│
└─ 否 → 是单用户/小团队/开发环境？
         ├─ 是 → ollama（最省事）
         └─ 否 → TGI
```

> ⚠️ **ollama 不适合生产并发**。它的调度是串行化的，
> 单卡消费级 GPU 上**并发 2 就已经饱和**（见 [05 章实测案例](05-benchmark-tuning.md)）。
> ollama 的价值是"5 分钟跑起来验证效果"，不是"服务 100 个用户"。

> ✅ **一个实用组合**：**开发期用 ollama 验证，生产用 vLLM**。
> 两者都提供 OpenAI 兼容接口，客户端代码可以完全不用改，
> 只切换 `base_url` 即可。这样开发效率和生产性能都能拿到。

## 3.7 服务化架构

一个"能交付"的服务，除了模型本身还需要这些：

```
              ┌──────────────────────────────────────────┐
   客户端 ───▶│  反向代理 / API 网关                       │
 (业务系统)    │  · TLS 终止   · 鉴权（API Key/JWT）        │
              │  · 限流       · 请求日志   · 负载均衡       │
              └───────────────┬──────────────────────────┘
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
      ┌───────────────┐               ┌───────────────┐
      │ 推理实例 1     │               │ 推理实例 2     │
      │ vLLM :8000    │               │ vLLM :8001    │
      │ GPU 0-3       │               │ GPU 4-7       │
      └───────┬───────┘               └───────┬───────┘
              │                               │
              └───────────────┬───────────────┘
                              ▼
      ┌──────────────────────────────────────────────┐
      │ 可观测性                                      │
      │  DCGM Exporter ──┐                            │
      │  vLLM /metrics ──┼──▶ Prometheus ──▶ Grafana  │
      │  日志 ───────────┴──▶ Loki / ELK              │
      │                     告警 ──▶ 邮件/钉钉/企微    │
      └──────────────────────────────────────────────┘
```

### 各组件要点

| 组件 | 要求 | 说明 |
| --- | --- | --- |
| **API 网关** | 必须 | Nginx / APISIX / Kong / Traefik 均可 |
| **鉴权** | 生产必须 | 至少 API Key；对外暴露建议 JWT |
| **限流** | 强烈建议 | 防止单客户端打满；按 QPS 和并发连接数双重限制 |
| **超时设置** | 容易忽略 | 流式接口超时要设**大**（如 300s），否则长回答被掐断 |
| **多副本负载均衡** | 高可用需要 | 注意**会话粘性**：多轮对话最好固定到同一副本，可提高前缀缓存命中 |
| **健康检查** | 必须 | 探针应检查 `/health` 而非仅端口，且**首次加载期间不能判失败** |

> ⚠️ **健康检查探针的经典坑**：大模型启动要几分钟（加载 145 GB 权重），
> 如果 K8s liveness probe 设成 `initialDelaySeconds: 30`，
> 容器会被反复杀掉重启，**永远起不来**。
> 应该设 `initialDelaySeconds` ≥ 模型加载时间，或改用 `startupProbe`。

## 3.8 容量规划与高可用

### 3.8.1 容量规划表（方案里应该有的）

| 项 | 计算依据 | 结果 |
| --- | --- | --- |
| 单副本并发能力 | 算例 3.3.4 | 89 路 |
| 单副本吞吐 | 压测实测（见 05 章） | ___ tok/s |
| 目标业务并发 | 客户提供 | ___ 路 |
| 需要副本数 | 目标并发 / 单副本并发 × 1.3 | ___ 个 |
| 所需卡数 | 副本数 × 单副本卡数 | ___ 张 |
| 峰值显存 | `nvidia-smi` 实测 | ___ GB / ___ GB |

### 3.8.2 高可用的三个层次

| 层次 | 做法 | 成本 |
| --- | --- | --- |
| **L1 进程级** | systemd / supervisor 守护，进程挂了自动重启 | 低 |
| **L2 副本级** | 多副本 + 网关负载均衡，一个副本挂了流量切走 | 中 |
| **L3 节点级** | 多机部署，单机故障不影响服务 | 高 |

> ⚠️ **必须和客户明确 SLA 到哪一层**。
> 单副本部署**无法做到高可用** —— 重启期间服务中断（大模型重启要几分钟）。
> 如果客户要求 7×24 不中断，就必须多副本，卡数翻倍，报价要跟上。

### 3.8.3 降级预案（方案设计阶段就要想）

| 触发条件 | 降级动作 |
| --- | --- |
| 并发超限 | 队列排队 + 返回"繁忙"提示，而非无限等待 |
| 显存紧张 | 动态缩短 `max_tokens` |
| 副本故障 | 流量切到健康副本，同时按容量降级（限流） |
| 整体不可用 | 切换到备用小模型（如 7B）保底可用 |

## 3.9 方案说明书应该包含什么

一份客户会签字的方案说明书，至少包含：

1. **需求与目标**（业务语言 + 量化指标）
2. **环境现状**（引用勘察表）
3. **模型选型**（含候选对比与选型理由、许可协议说明）
4. **精度方案**（量化选择 + 精度对比测试结果）
5. **资源规划**（显存估算过程、卡数、并行策略）
6. **性能目标**（可量化 + 带前提条件，见 [06 章 6.3](06-acceptance.md)）
7. **服务架构**（部署架构图、组件清单）
8. **交付物清单**（DEL 编号列表）
9. **里程碑与工期**
10. **风险与假设**（列出所有"以客户提供 X 为前提"的项）
11. **验收标准**（提前明确，避免验收时扯皮）

> ✅ **第 10 项"风险与假设"是最有保护作用的一节**。
> 例如写上："本方案假设客户在 P4 阶段前完成驱动升级至 550+；
> 若驱动无法升级，则 CUDA 12.4 相关组件不可用，需重新评估方案。"
> 这一句能在后续扯皮时省掉大量时间。
