# 08 交付物与模板

> **目标**：让每一次交付都产出**同一套、可复用、可追溯**的文档。
>
> 原则：**宁可多写一页，不留下一个说不清的地方。**

---

## 8.1 为什么交付物比技术更重要

技术做得再好，如果没有文档：

- 客户不知道你的服务有什么限制 → 误用 → 出问题算你的
- 客户不知道怎么巡检 → 出了隐患发现不了 → 上线一个月后崩溃
- 客户不知道边界在哪 → 会不断提出"顺便支持一下 XX"
- 交接人员离职后 → 所有知识归零

> ✅ **交付物的本质是"责任的边界线"**。
> 写清了，双方都轻松；没写清，怎么都是你的事。

## 8.4 DEL-03 部署方案说明书 / DEL-04 部署架构图

### 方案说明书目录（照这个结构写）

```markdown
1. 文档信息（版本 / 日期 / 编写人 / 审核人）
2. 项目背景与目标
   2.1 业务场景
   2.2 量化目标（并发数、延迟要求、可用性要求）
3. 环境现状
   3.1 硬件现状（引用 DEL-01）
   3.2 软件现状
   3.3 限制条件（无外网 / 无法升驱动 / 变更窗口等）
4. 方案设计
   4.1 模型选型（含候选对比表与选型理由、许可协议说明）
   4.2 精度方案（量化选择 + 精度对比测试结果）
   4.3 资源规划（显存估算过程，照 03 章 3.3.4 的算例格式）
   4.4 并行策略（TP/PP/DP 选择依据）
   4.5 引擎选型（对比表 + 选择理由）
   4.6 服务架构（图 + 组件清单）
   4.7 容量规划（单副本能力 → 所需副本 → 所需卡数）
5. 交付物清单（DEL-01 ~ DEL-17）
6. 里程碑与工期
7. 风险与假设        ← 最有保护作用的一节
8. 验收标准          ← 必须可量化、带前提条件
9. 附录（估算公式、参考数据、对比测试结果）
```

### 架构图要点

一张合格的部署架构图应包含：

- 网络分区（DMZ / 内网 / 管理网）
- 客户端 → 网关 → 推理实例 → GPU 的链路
- 端口号标注
- 监控链路（指标、日志、告警的去向）
- 数据流向（哪些数据出网、哪些不出）
- 高可用说明（哪些组件有副本）

> ✅ **画架构图的一个实用技巧**：用 Mermaid 或纯 ASCII 写在
> Markdown 里，而不是画成图片。这样它可以被 diff、被改动、
> 被复制，而且不依赖绘图工具。

## 8.5 DEL-08 压测报告 / DEL-09 验收测试报告

### 压测报告结构

```markdown
# 推理服务压测报告

## 1. 测试目标
（要回答什么问题：能扛多少并发？瓶颈在哪？）

## 2. 测试环境        ← 必须详细，否则数据不可复现
- 硬件配置（完整）
- 软件版本（完整）
- 服务启动参数（完整粘贴）
- 客户端配置（工具、版本、压测机配置）

## 3. 测试方法与口径定义   ← 最容易引起争议，必须写清
- TTFT 定义：从 ______ 到 ______
- TPOT 定义：
- 吞吐定义：
- 是否含排队时间：是 / 否
- 输入/输出长度、并发梯度、预热次数、时长
- 温度与随机种子

## 4. 测试结果
- 主结果表
- 曲线图
- 资源占用（显存/利用率/温度）
- 错误情况

## 5. 结论
- 吞吐饱和点在哪
- 瓶颈是算力还是调度（附判读依据）
- 推荐的生产配置（并发上限、副本数）

## 6. 数据适用边界     ← 别省这一节
- 本组数据能说明什么
- 不能说明什么
- 引用时的表述建议

## 7. 附录
- 原始数据文件
- 完整日志
```

> ⚠️ **"数据适用边界"这一节是专业性的体现**。
> 任何一组压测数据都有前提，"在 A 硬件 B 模型 C 配置下"。
> 主动写清边界的报告，比只给一堆漂亮数字的报告可信得多。

### 验收测试报告结构

```markdown
# 验收测试报告

## 1. 验收信息
- 验收时间 / 地点 / 参与人
- 验收依据（引用的方案文档编号与版本）

## 2. 功能验收结果
（逐条用例的表格：用例编号、操作、预期、实际、判定）

## 3. 性能验收结果
（按 06 章 6.3 的四要素：前提 + 负载 + 指标 + 阈值，逐项判定）

## 4. 稳定性验收结果
- 长稳时长与曲线
- 显存趋势
- 错误率
- 故障恢复测试结果

## 5. 可复现性验证
（两次压测的对比）

## 6. 未通过项与处置
（问题、根因、整改措施、计划完成时间）

## 7. 验收结论
□ 全部通过  □ 通过（附整改项）  □ 不通过

## 8. 签字
```

## 8.6 DEL-11 运维手册（客户版）

**注意：这是给客户运维看的，不是给你自己看的。**

### 写作三原则

| 原则 | 说明 |
| --- | --- |
| **只写"怎么做"，不写"为什么"** | 客户不需要理解 PagedAttention 的原理 |
| **命令可直接复制** | 不要写 `<你的容器名>`，要写实际的名字或用变量说明 |
| **明确边界** | 哪些客户可以自己动，哪些必须联系交付方 |

### 建议目录

```markdown
1. 系统概述（这是什么、提供什么能力、架构图）
2. 日常操作
   2.1 查看服务状态
   2.2 启动 / 停止 / 重启服务
   2.3 查看日志
   2.4 查看监控面板
3. 日常巡检
   3.1 巡检清单（引用 DEL-12）
   3.2 巡检脚本使用方法
   3.3 什么情况算异常
4. 常见问题处理
   4.1 服务无响应 → 怎么做
   4.2 请求报错 → 怎么排查
   4.3 磁盘满了 → 怎么清理
   4.4 收到 XX 告警 → 怎么处理
5. 变更管理
   5.1 什么可以改（如：并发上限？一般不可以）
   5.2 什么绝对不能改
   5.3 变更流程
6. 应急
   6.1 三级降级方案
   6.2 重启流程
   6.3 回滚流程
   6.4 应急联系人
7. 报障模板
8. 附录
   8.1 参数说明（简要）
   8.2 端口与路径清单
   8.3 版本信息
```

> ⚠️ **第 5 章"变更管理"必须写清"什么绝对不能改"**。
> 例如：不要手动 `docker rm` 容器、不要改 vLLM 启动参数、
> 不要在模型目录里增删文件、不要升级 GPU 驱动而不通知。
> **客户改了之后出问题，责任很模糊，所以要提前立规矩。**

## 8.7 DEL-15 培训 + DEL-16 交接确认单

### 培训材料大纲

| 模块 | 内容 | 时长 |
| --- | --- | --- |
| 1. 系统概览 | 架构、组件、数据流 | 20 min |
| 2. 日常操作 | 演示：启停、看日志、看监控 | 40 min |
| 3. **实操演练** | **让客户自己重启一次、巡检一次** | 30 min |
| 4. 常见问题 | 演示：模拟一次故障并处理 | 30 min |
| 5. 应急与报障 | 流程、联系人、模板 | 20 min |
| 6. 答疑 | — | 20 min |

> ✅ **第 3 模块"实操演练"是必须的。**
> 讲了不等于会了。**让客户运维当场做一遍，才算真的移交。**
> 这也顺便验证了你的运维手册写得够不够清楚 ——
> 如果他照着手册做不出来，说明手册要改。

## 8.8 DEL-17 版本变更记录

```markdown
# 版本变更记录

| 日期 | 版本 | 变更类型 | 变更内容 | 变更人 | 影响评估 | 回滚方式 | 验证结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| | | 参数 | | | | | |
| | | 镜像 | | | | | |
| | | 模型 | | | | | |
| | | 驱动 | | | | | |
```

**变更类型与风险等级：**

| 类型 | 风险 | 是否需要重测 | 是否需要客户审批 |
| --- | --- | --- | --- |
| 参数微调 | 低 | 压测抽测 | 通知即可 |
| 参数大改（并发/长度） | 中 | 完整压测 | **需要** |
| 镜像升级 | 中高 | 功能 + 性能 | **需要** |
| 模型替换 | 高 | **全部重测** | **需要，且需重新验收** |
| 驱动升级 | 高 | 功能 + 性能 | **需要** |

> ⚠️ **"模型替换"在验收上是等价于一次新交付的**。
> 不要因为是"同一个模型的更新版本"就跳过验收。
