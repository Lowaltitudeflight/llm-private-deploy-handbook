# 01 交付总览

> 本章定义"一次私有化交付"包含哪些阶段、每个阶段的产出和准出条件、
> 谁在什么时候要交什么。开工前先把这一章过一遍，能避免 80% 的返工。

---

## 1.1 私有化交付到底在交付什么

客户买的不是"一个模型"，而是**一个能长期稳定运行、有人能维护的推理服务**。
所以交付的终态包含四层：

| 层 | 内容 | 交付物形态 |
| --- | --- | --- |
| **① 硬件与基础环境** | GPU / 驱动 / CUDA / 容器运行时 / 网络 | 已配置好的机器 + 配置基线记录 |
| **② 推理服务** | 引擎 + 模型 + 参数 + 网关 + 鉴权 | 可用的 API 端点 + 启动脚本 |
| **③ 可观测性** | 指标采集 + 面板 + 告警 + 日志 | Grafana 面板 + 告警规则 + 日志规范 |
| **④ 知识与责任转移** | 文档 + 培训 + 验收 + 售后边界 | 运维手册 + 培训记录 + 验收单 |

**很多交付只做到 ② 就结束了**，客户上线两周后 GPU 掉卡，没人知道怎么看，
于是变成"你们交付的系统不稳定"。第 ③ ④ 层才是把责任真正划清的部分。

## 1.2 八阶段交付模型

```
 P1 售前支持 ──▶ P2 环境勘察 ──▶ P3 方案设计 ──▶ P4 实施部署
   (POC/额度)      (Go/No-Go)      (方案签字)       (服务可访问)
                                                        │
                                                        ▼
 P8 售后运维 ◀── P7 正式移交 ◀── P6 试运行 ◀────── P5 压测与验收
   (SLA/工单)      (运维交接)      (观察期)         (验收单签字)
```

### 各阶段输入 / 输出 / 准出条件

#### P1 售前支持

| 项 | 内容 |
| --- | --- |
| **输入** | 客户业务场景、预计并发、数据敏感等级、预算 |
| **动作** | 判断可行性（模型规模 vs 预算内硬件）；必要时做小规模 POC |
| **输出** | 技术可行性意见 + 硬件建议清单 |
| **准出** | 硬件清单与模型规模**在显存上算得通**（见 [03 章](03-solution-design.md)） |

> ⚠️ **这一步最常见的坑**：商务先承诺了"72B 模型 + 8 张 24G 卡跑 FP16"，
> 而 72B FP16 光权重就要 144 GB，8×24G = 192 GB 里还要塞 KV Cache
> 和框架开销，长上下文直接 OOM。**勘察和估算一定要在报价前做。**

#### P2 环境勘察

| 项 | 内容 |
| --- | --- |
| **输入** | 客户机房访问权限 |
| **动作** | 实测硬件、软件栈、网络、存储、供电、出网策略 |
| **输出** | **环境勘察表**（见 [附录 B](<../appendix/b-checklists.md>)）+ **Go/No-Go 判定** |
| **准出** | 所有"必须满足项"通过；有风险的项已有明确处置方案 |

详细内容见 [02 环境勘察与准入检查](02-environment-survey.md)。

#### P3 方案设计

| 项 | 内容 |
| --- | --- |
| **输入** | 环境勘察表 + 业务需求 |
| **动作** | 模型选型、显存估算、并行策略、引擎选型、服务化架构、容量规划 |
| **输出** | **部署方案说明书** |
| **准出** | 客户书面确认方案（尤其是模型版本、量化精度、性能目标） |

详细内容见 [03 部署方案设计](03-solution-design.md)。

> ⚠️ **量化精度必须客户签字确认**。因为量化会带来精度损失，
> 若客户后续拿"模型答得不如官网 Demo 好"来质疑，没有签字就很难解释。
> 建议同时保留一份 FP16 的对比测试结果。

#### P4 实施部署

| 项 | 内容 |
| --- | --- |
| **输入** | 已确认的方案 |
| **动作** | 装驱动、配容器、导模型、起服务、接通网关 |
| **输出** | 可访问的推理服务 + **部署记录表** |
| **准出** | 冒烟测试通过（能正常返回、流式正常、鉴权生效） |

详细内容见 [04 实施部署](04-deployment.md)。

#### P5 压测与验收

| 项 | 内容 |
| --- | --- |
| **输入** | 可运行的服务 + 约定的性能目标 |
| **动作** | 功能验收、性能压测、稳定性观察、可复现性验证 |
| **输出** | **压测报告** + **验收测试报告** + **验收单** |
| **准出** | 验收单双方签字 |

详细内容见 [05 压测与调优](05-benchmark-tuning.md)、[06 验收](06-acceptance.md)。

#### P6 试运行

| 项 | 内容 |
| --- | --- |
| **输入** | 已验收的服务 |
| **动作** | 客户真实流量接入，观察 1~4 周 |
| **输出** | 试运行观察记录 |
| **准出** | 观察期内无 P1/P2 级故障，或所有故障已闭环 |

> 试运行期要**明确写入合同**：期间发现的、由客户环境导致的故障（如机房断电、
> 交换机故障）不计入交付质量。否则试运行会变成无限期免费维护。

#### P7 正式移交

| 项 | 内容 |
| --- | --- |
| **输入** | 全部交付物 |
| **动作** | 运维培训、文档交接、账号权限交接、售后边界确认 |
| **输出** | **交接确认单** + 培训签到表 |
| **准出** | 客户运维人员能**独立完成一次重启和一次巡检** |

> ✅ **最好的验收方式**：让客户运维当场重启一次服务、看一次监控面板、
> 导出一次日志。他们做得出来，移交才算完成。

#### P8 售后运维

| 项 | 内容 |
| --- | --- |
| **输入** | 已移交的系统 |
| **动作** | 告警响应、版本升级、故障处理、容量扩容 |
| **输出** | 工单记录 + 版本变更记录 |
| **准出** | —（持续过程） |

## 1.3 角色与职责矩阵

小团队通常一人多角，但**职责边界必须说清楚**，否则出问题时会互相推。

| 角色 | 主要职责 | 关键交付物 | 不负责 |
| --- | --- | --- | --- |
| **交付工程师**（实施） | 勘察、部署、调优、写文档 | 部署记录表、压测报告、运维手册 | 商务承诺、硬件采购 |
| **方案/售前** | 可行性判断、硬件建议、报价 | 方案说明书 | 现场实施细节 |
| **项目经理** | 排期、客户沟通、风险跟踪 | 项目计划、会议纪要 | 技术判断 |
| **客户 IT / 运维** | 机房准入、网络开通、账号提供、接收培训 | 环境访问、验收签字 | 模型效果 |
| **客户业务方** | 提出业务需求、确认模型效果 | 需求确认、效果验收签字 | 系统稳定性 |
| **原厂/硬件厂商** | 硬件质保、掉卡更换 | 硬件报修单 | 应用层问题 |

**边界模糊地带与建议归属**：

| 问题 | 建议归属 | 理由 |
| --- | --- | --- |
| 客户网络策略导致服务不通 | 客户 IT | 交付方只保证"服务在本机可访问" |
| 模型对业务问题答得不好 | 需在 P3 明确 | 属于选型问题，不是部署缺陷 |
| GPU 掉卡 | 硬件厂商 | 交付方负责定位并出报文 |
| 依赖库版本冲突 | 交付方 | 环境由交付方搭建 |
| 客户自行改了配置导致故障 | 客户 | 需在运维手册里写明"变更需通知交付方" |

## 1.5 常见踩坑（交付视角）

下面这些是**在交付现场真实会遇到的**，按发生频率排序：

### 坑 1：到了现场才发现硬件和清单不一致

报价单写 A100 80G，现场是 A100 40G；说好 8 卡，实际只有 6 卡在机箱里。
**对策**：P2 阶段必须**实际登录机器跑 `nvidia-smi`**，不接受"清单上说"。

### 坑 2：显存估算只算权重，不算 KV Cache

```
只算权重：72B × 2 bytes = 144 GB   ✅ 看起来 8×24G 刚好
加上 KV：32768 上下文 × 0.31 GB/1k tokens ≈ 10 GB
加上框架开销：~2 GB
→ 实际需要约 156 GB / 192 GB，只剩 36 GB 余量，并发一上来就 OOM
```

**对策**：估算公式见 [03 章 3.3](03-solution-design.md)，记得乘 **1.2~1.3 的安全系数**。

### 坑 3：客户环境完全不出网

内网隔离环境里 `pip install` / `docker pull` / `huggingface-cli download` 全部失败。
**对策**：勘察阶段就确认出网策略，提前准备离线包（见 [02 章 2.6](02-environment-survey.md)）。

### 坑 4：验收标准和客户理解不一致

交付方认为"能返回结果就算通过"，客户认为"要能扛住 100 并发"。
**对策**：P3 阶段把性能目标写成**可量化 + 带前提条件**的形式，
例如"并发 16、输入 1K / 输出 256 tokens 时，TTFT P95 ≤ 2 s，吞吐 ≥ 500 tok/s"。

### 坑 5：模型权重没校验，加载时报诡异错误

分片下载中断导致 `model-00003-of-00008.safetensors` 只有一半。
**对策**：下载后校验 `sha256` 与文件大小（见 [04 章 4.3](04-deployment.md)）。

### 坑 6：没有留下"干净基线"，后续无法判断问题

上线时没记录驱动版本、服务参数、显存占用。两周后出问题，无法判断是"变了"还是"一直这样"。
**对策**：DEL-02 版本基线记录 + DEL-05 部署记录表，**每次变更也要记**。

### 坑 7：把 demo 通过当成交付完成

能对话 ≠ 能服务。demo 是单用户、短文本、无并发；
生产是多用户、长文本、有并发、要鉴权、要监控。
**对策**：P4 的冒烟测试与 P5 的性能验收是两回事，都要做。

## 1.6 排期与人力参考

以下是**单机 8 卡、单一模型、标准流程**的经验区间，仅供参考：

| 阶段 | 典型工期 | 人力 |
| --- | --- | --- |
| P1 售前支持 | 2~5 天 | 方案 0.2 人 |
| P2 环境勘察 | 1~3 天（含差旅） | 实施 1 人 |
| P3 方案设计 | 2~5 天 | 方案 + 实施 |
| P4 实施部署 | 2~5 天 | 实施 1 人 |
| P5 压测与验收 | 3~7 天（含长稳观察） | 实施 1 人 |
| P6 试运行 | 1~4 周 | 值守 0.2 人 |
| P7 正式移交 | 1~2 天 | 实施 1 人 |

**最容易低估的是 P5**：一次 72 小时长稳观察就是 3 天，加上复测和报告，
一周很正常。排期时不要把它算成半天。
