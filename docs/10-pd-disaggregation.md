# 10 PD 分离推理架构（Prefill/Decode Disaggregation）

> **目标**：当单实例混合部署出现"长输入阻塞在线请求"或"预填充打断解码批次"时，用 PD 分离把两个阶段拆到独立实例上，各自独立扩缩与调优。
>
> 本章全部数据来自 8 卡跨架构试验台实测（2026-11：8 × RTX PRO 5000 72GB + 8 × H200 NVL 144GB，DeepSeek-V4.1-Flash 476GB 权重）。配套脚本与完整工程档案见 [pd-disaggregation-deepseek](https://github.com/Lowaltitudeflight/pd-disaggregation-deepseek)。

---

## 10.1 先判断：你需要 PD 吗

PD 不是万能架构——**同样的显存预算，PD 与独立副本的权重总量相同**（每个节点都要加载完整模型），它的收益在延迟隔离与扩缩灵活性，不在显存节省。按场景选形态：

| 场景 | 推荐形态 | 理由 |
| --- | --- | --- |
| 长输入与短请求混部，长输入阻塞在线请求 | **单机 4+4** 或 **跨机** | 预填充与解码物理隔离 |
| 只需要更高吞吐，无干扰问题 | **双实例 + 负载均衡** | 同样显存换来 2 份完整服务能力，无 KV 传输开销 |
| 在线与批量混部、利用率与 SLO 并重、规模 ≥16 卡 | **跨机 PD（非对称 P:D）** | P:D 比例可调，解码批次平稳支撑利用率 |
| 低并发 / 训练为主 / 卡少 | **独立副本** | PD 的权重双份成本与传输开销不划算 |

**先做干扰测试再决策**：3 个 128K 级预填充并发期间测短请求 TTFT。实测恶化 18.2 倍才值得上 PD；如果像 11K 级输入那样几乎无影响（1.1×），独立副本更简单。

## 10.2 必要性实测：混合部署的干扰效应

单节点 TP4（DeepSeek-V4.1-Flash），短请求 TTFT 实测：

| 场景 | 短请求 TTFT | 恶化倍数 |
| --- | --- | --- |
| 空闲期 | 0.04 s | 1.0× |
| 1 个 11K 预填充并发 | 0.05 s | 1.1× |
| 3 个 128K 级预填充并发 | 0.79 s | **18.2×** |

结论：预填充对在线请求的阻塞只在大输入并发时出现。**先量化再上架构**，避免为不存在的问题付复杂度成本。

## 10.3 引擎选型（动手前先看）

对 DeepSeek-V4.1 类模型（MLA 注意力 + 稀疏检索索引器 + KV 压缩器的复合 KV 结构），PD 传输组件的兼容性差异极大：

| 引擎 / 传输组件 | 结果 | 现象与根因 |
| --- | --- | --- |
| vLLM 0.32.0 + NIXL（pull） | ❌ | 传输层 12 次全成功、prefix cache 命中 99.8%，但 D 端输出退化为重复 token——索引器/压缩器的 scratch 页与主 KV 页地址重叠，传输组未覆盖完整状态 |
| vLLM + HiSparse MultiConnector | ❌ | 初始化崩溃：worker 在 engine core 解析 KV 布局前取值（时序缺陷） |
| vLLM + NIXL Push | ❌ | P 端握手正常，D 端请求超时挂死 |
| **SGLang + Mooncake TCP / NIXL** | ✅ | 两跳链路验证通过，输出正确，128K 长输入全过 |
| TensorRT-LLM | 待验证 | 列入目标环境验证计划 |

**选型结论**：该类模型用 SGLang 做 PD 引擎。若项目默认 vLLM，先在试验台验证 KV 传输后再上规模——三种连接器的失败模式（内容损坏 / 初始化崩溃 / 挂死）在 8 卡上花两周才排完。

## 10.4 形态一：单机 4+4（最快见效）

单机 8 卡拆两半：4 卡 Prefill + 4 卡 Decode，KV 走机内回环。

**实测（P：4×PRO 5000，D：4×H200，跨架构混部）**：

| 测试项 | 结果 |
| --- | --- |
| 上下文长度 | 131,072 token |
| 126K 长输入 | 5.81 s（校验正确） |
| 2 × 63K 并发 | 5.22 / 5.17 s（真并行） |
| 预填充期间短请求 TTFT | 0.19 s（无劣化） |
| 20 项混合负载 soak | 0 失败，显存零漂移 |

**启动要点**（完整脚本见仓库 `deploy/single-4plus4/`）：

```bash
# 两端共同参数
--tp-size 4 --ep-size 4 --context-length 131072 \
--max-running-requests 2 --chunked-prefill-size 8192 \
--kv-cache-dtype fp8_e4m3 --mem-fraction-static 0.96 \
--max-total-tokens 400000          # ← 最关键的一行，见 10.7

# P 端
--disaggregation-mode prefill --disaggregation-transfer-backend mooncake_tcp \
--disaggregation-bootstrap-port 8998 --port 8100
# D 端：mode=decode --port 8000 --disaggregation-bootstrap-port 8999
# 路由器：sglang_router.launch_router --pd-disaggregation \
#   --prefill http://127.0.0.1:8100 8998 --decode http://127.0.0.1:8000
```

**注意**：启动顺序必须先 P 后 D；TP 分组与 NVLink 岛对齐（跨岛的 TP8 在无 NVLink 机器上 all-reduce 走 UPI，性能显著下降）。

## 10.5 形态二：双实例 + 负载均衡（同卡数产能翻倍）

同样的 8 卡，跑两个完整副本（各 TP4）+ 网关轮询。与 4+4 PD 的实测对比：

| 维度 | 双实例 2×TP4 | PD 4+4 |
| --- | --- | --- |
| 有效产能 | **2 个完整副本** | 1 个（P+D 合计） |
| 最大并发（128K） | **约 16** | 2 |
| 126K TTFT | **0.46 s** | 13.46 s（跨机）/ 5.81 s（同机） |
| 长 prompt 阻塞短请求 | 靠负载均衡近似隔离 | 原生消除 |

**结论**：显存预算相同（权重各存两份），双实例产能翻倍。PD 只在"长输入阻塞"成为实测痛点、且负载均衡无法缓解时才值得选。

## 10.6 形态三：跨机分离（网络是第一约束）

跨机后 KV 需要真实走网络。先算账再买设备：

**KV 体积公式**：`token 数 × 每 token KV 字节`。MLA 结构（FP8）约 **22.5 KB/token**；
普通 GQA 模型（8 KV heads）约 260 KB/token——**差一个数量级，跨机 PD 前先看模型结构**。

**带宽需求公式**：`Gbps ≈ 5 × 每 token KV ÷ 每 token 预填充时间`（20% 开销标准）。

千兆链路实测梯度（128K 配置）：

| 配置上下文 | 实际输入 token | TTFT | 隐含传输速率 |
| --- | ---: | ---: | --- |
| 16K | 16,225 | 2.998 s | 122 MB/s（≈线速） |
| 64K | 65,373 | 16.314 s | 90 MB/s |
| 128K | 130,914 | 25.714 s | 115 MB/s |

128K 的 TTFT 中**传输占比 ≥95%**（2.95 GB ÷ 115 MB/s）。同模型单机 TTFT 仅 0.46s——**千兆下跨机 PD 慢 56 倍，只适合离线/后台任务**。

| 链路 | 128K KV 传输 | 判定 |
| --- | --- | --- |
| 千兆 | 25 s | ❌ 交互不可用 |
| 25G TCP | 1.2 s | ✅ 解锁交互 |
| 100G RoCE | 0.26 s | ✅ 宽裕 |
| 800G IB | 0.03 s | 归零 |

**网卡选型提示**：Mellanox ConnectX（厂商 ID `15b3`）对 RDMA 支持最成熟；Intel X710 仅 iWARP、无 RoCE，主流传输组件不友好——避开。

## 10.7 关键参数经验（四个坑，每个都实测过）

| 参数 | 默认行为的问题 | 实测修正 |
| --- | --- | --- |
| `--max-total-tokens` | **默认按显存满配分配 KV 池，实际超配约 8 倍**（实测 210 万 token，需求仅 26 万），挤占预填充激活显存导致 OOM | 显式限池后 chunked-prefill 2048 → 8192（4×），可用显存 5.7 → 8.1 GB/卡，并发时短请求 TTFT 0.45 → 0.19 s |
| `--max-running-requests` | 过高导致 SWA 池超配、上下文受限 | 甜点值 2：吞吐接近 4 并发（差 5.6%），延迟减半 |
| `--chunked-prefill-size` | 默认 8192 在受限显存下 OOM（曾被误判为内核 bug，nanobind leak 只是被杀时的伴生现象） | 先限 KV 池，再放分块；两者联调而非单独硬顶 |
| KV 缓存精度 | 默认解析为 fp8_e4m3 | 维持 fp8（22.5 KB/token 口径的前提） |

**KV 池超配是最隐蔽的一个**：它把"分块大小上不去"伪装成"显存不足的 OOM"，容易误判为内核或驱动问题。排查顺序：先看 `max_total_num_tokens` 与实际并发需求的比值，再怀疑其他。

## 10.8 故障域与自愈

PD 的故障域模型：**P 实例故障不中断 D 端已建立会话的生成，但阻断新请求**。D 端已有会话继续生成至自然结束，新请求在 P 恢复前收到 503。

实测（注入真实故障：`kill -9` P 端 TP worker）：

```
T+0     P 端 TP0 worker 被杀，其余 3 个 rank 因连接断开退出，容器退出
T+90s   看门狗（30s 间隔 × 3 次阈值）确认异常
T+90s   自动按 P → D → 路由器顺序重建
T+250s  全栈恢复，P/D/路由器全部 200，服务正常
```

生产部署要点：看门狗（30s 间隔、连续 3 次失败才动作，防误判）；容器 `--restart unless-stopped` 兜底容器级死亡；网关将不健康的 P 摘除并返回 503（而非挂死）。

## 10.9 风险登记

| 风险 | 等级 | 说明 |
| --- | --- | --- |
| 输出质量等价性 | 高 | 为兼容跨代卡采用了关闭候选块加速的兼容配置，与模型默认配置的输出质量等价性尚未评估；同构集群无此问题，但需确认 |
| 多 P 多 D 形态 | 中 | 路由器原生支持多实例（`--prefill` 可写多行），未实测 |
| 新架构引擎适配 | 中 | 新卡首批部署存在内核/算子兼容风险（试验台在 Blackwell sm_120 上即遇到稀疏 MLA 内核不匹配），预留 bring-up 时间 |
| KV 传输校验与加密 | 中 | 多租户环境需评估端到端校验 |
